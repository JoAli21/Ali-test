# ملخص أوامر Git و GitHub (مادة Software Maintenance)

- هذا الملف مرجع سريع مبني على ملازم المادة: Lab 1 و Lab 4-5 و Lab 6 ومحاضرة GitHub عبر Godot، وعلى ما نفذناه عملياً.
- الأوامر تُكتب في terminal من نوع Git Bash داخل VS Code: من قائمة Terminal اختر New Terminal ثم اختر bash.
- الأوامر تُنفذ داخل مجلد المشروع، إلا إذا ذُكر غير ذلك.

## الأوامر الأساسية بسرعة: إضافة ملف وتعديله ورفعه

- الأمر `git status` : يفحص الحالة، يعني أي ملفات جديدة أو معدلة. الأحمر لم يُجهّز، والأخضر جاهز للحفظ.
- الأمر `git add README.md` : يجهّز هذا الملف فقط للحفظ، سواء كان جديداً أو معدلاً.
- الأمر `git add .` : يجهّز كل الملفات الجديدة والمعدلة في المجلد دفعة واحدة.
- الأمر `git commit -m "Add README"` : يحفظ التغيير محلياً مع رسالة تشرح ماذا فعلت.
- الأمر `git push origin master` : يرفع الـ commits من جهازك إلى GitHub، فيظهر الملف في الصفحة الرئيسية للمستودع.
- الأمر `git pull origin master` : ينزّل آخر تغييرات GitHub إلى جهازك، ويفيد قبل الرفع إذا تغير شيء من مكان آخر.
- الأمر `git log --oneline` : يعرض الـ commits بسطر واحد لكل commit.
- الأمر `git diff` : يعرض ما تغير في الملفات قبل التجهيز.
- الأمر `git restore <ملف>` : يرجع الملف إلى آخر حالة محفوظة ويلغي تعديلاتك غير المحفوظة.
- لإضافة ملف جديد: أنشئه داخل المجلد ثم `git add اسم-الملف` ثم `git commit -m "..."` ثم `git push origin master`.
- لتعديل ملف موجود: عدّله واحفظه بـ Ctrl + S ثم نفس الأوامر الثلاثة: add ثم commit ثم push.
- GitHub README : يظهر ملف README.md تلقائياً أسفل قائمة الملفات في صفحة المستودع، ويُعرض بصيغة Markdown منسقة.

## أولاً: المفاهيم الأساسية

### لماذا نحتاج التحكم بالإصدارات (Version Control)

- المشكلة بدون نظام: ثلاثة مطورين يعدّلون نسخاً مختلفة من المشروع، فمن يملك آخر نسخة؟ وكيف ندمج التغييرات دون ضياع عمل أحد؟
- ضياع التاريخ: يصعب معرفة من غيّر الملف وماذا تغيّر ومتى.
- نسخ مربكة: ملفات اسمها final و final2 و final_latest.
- خطر التعاون: قد يكتب عضو فوق تغييرات عضو آخر.
- غياب المراجعة: لا توجد طريقة منظمة لمناقشة التغيير والموافقة عليه.
- النسخ اليدوية: مجلدات كثيرة مكررة وتاريخ غير واضح ومن الصعب مقارنة التغييرات.
- التحكم بالإصدارات: تاريخ تغييرات موثق واحد، ويُسجل المؤلف والوقت، ويمكن مقارنة الإصدارات أو استرجاعها، ويمكن دمج العمل المتوازي.
- نظام التحكم بالإصدارات (VCS) يسجل التغييرات على ملفات المشروع عبر الزمن، ويجيب عن: ماذا تغيّر؟ ومن غيّره؟ ومتى؟

### مركزي وموزع

- الـ VCS المركزي (Centralized): خادم مركزي يخزن تاريخ الإصدارات الرئيسي، ويعتمد المطور على الخادم في أغلب العمليات.
- الـ VCS الموزع (Distributed): كل نسخة (clone) فيها تاريخ المستودع كاملاً، ويستطيع المطور أن يعمل commit محلياً ويزامن لاحقاً.
- الـ Git نظام موزع.

### ثلاثة أشياء مختلفة: Git و GitHub و VS Code

- الـ Git : محرك التحكم بالإصدارات، يعمل على جهازك ويتتبع التغييرات في مستودع محلي، وفيه أوامر add و commit و branch و merge و log.
- الـ GitHub : منصة تعاون تستضيف مستودعات Git على الإنترنت، وتدعم المشاركة وإدارة الصلاحيات والمراجعة، وتضيف Issues و Pull Requests و Actions و Projects.
- الـ VS Code : محرر كود وبيئة عمل فيها دمج مع Git.
- الـ GitHub يستخدم Git، لكن Git لا يحتاج GitHub ليعمل.
- منصات أخرى مشابهة لـ GitHub: GitLab و Bitbucket، والاختيار حسب متطلبات المشروع.
- مثال الدراسة: Godot مشروع مفتوح المصدر (محرك ألعاب 2D و 3D)، وعنوانه `github.com/godotengine/godot`. Godot هو المشروع، و Git يتتبع إصداراته، و GitHub يستضيف العمل وينسقه.

### الـ commit

- الـ commit يمثل نقطة مهمة في تاريخ المشروع، ويحفظ: لقطة (snapshot) من محتوى الملفات المختارة، ومعلومات المؤلف والوقت، ورسالة قصيرة تشرح لماذا حدث التغيير، ورقماً فريداً (hash) نرجع به لذلك الإصدار.
- كل commit يشير إلى الـ commit الذي قبله (parent).
- المشروع يتطور عبر commits، مثل: إنشاء المشروع ثم إضافة ميزة ثم إصلاح خطأ ثم إعادة هيكلة الكود.

### الصورة العامة لسير عمل Git (Basic Git workflow)

- الملفات تمر بأربعة أماكن بالترتيب: مجلد العمل (Working Directory) ثم منطقة التجهيز (Staging Area) ثم المستودع المحلي (Local Repository) ثم المستودع البعيد (Remote) على GitHub.
- مجلد العمل: المجلد الذي تنشئ فيه الملفات وتعدّلها وتحذفها. تعديل الملف لا ينشئ commit تلقائياً. والأمر `git status` يعرض حالته.
- منطقة التجهيز (Staging Area أو Index): مكان تجهيز الـ commit القادم. والـ commit يسجل ما كان مجهّزاً فقط، ويمكن تجهيز بعض التغييرات دون كلها.
- المستودع المحلي: يخزن الـ commits والتاريخ على جهازك. يُحفظ الـ commit محلياً قبل أن يُرفع إلى أي مكان، ويمكن فحص commits قديمة بدون إنترنت.
- الأمر `git add` : ينقل التغييرات من مجلد العمل إلى منطقة التجهيز.
- الأمر `git commit` : ينقلها من منطقة التجهيز إلى المستودع المحلي، أي يحفظ لقطة.
- الأمر `git push` : يرفع المستودع المحلي إلى المستودع البعيد على GitHub.
- الأمر `git pull` : يعمل بالاتجاه المعاكس، ينزّل من GitHub إلى جهازك.
- الأمر `git reset` : يرجع الملفات من منطقة التجهيز إلى مجلد العمل، أي يلغي التجهيز.
- الأماكن الثلاثة الأولى على جهازك (Local)، والرابع فقط على GitHub (Remote).
- الدورة الأساسية: عدّل الملفات، ثم افحص بـ `git status`، ثم جهّز بـ `git add`، ثم احفظ بـ `git commit`. وكرر الدورة كلما تقدم العمل، والرفع يأتي بعد إعداد remote.

### المستودع والمشروع ليسا نفس الشيء

- الـ Repository (المستودع): يخزن ملفات المصدر والـ commits والـ branches وتاريخ التطوير.
- الـ GitHub Project (المشروع): ينظم عناصر العمل بصرياً بجدول أو لوحة مثل Kanban، وفيه بطاقات وحالات وأولويات ومسؤولين وتقدم.
- قد يُستخدم المستودع نفسه مع ميزات إدارة المشروع، وقد يغطي Project أكثر من مستودع.
- مثال: `godotengine/godot` مستودع، أما الـ Project فهو عرض تخطيط منفصل.

## ثانياً: العمل العملي خطوة خطوة

### المرحلة 1: إنشاء مشروع محلي

- أنشئ مجلداً جديداً وادخله، مثلاً بالأمرين `mkdir LabWorkspace` ثم `cd LabWorkspace`، أو أنشئه على سطح المكتب وافتحه في VS Code من File ثم Open Folder.
- أنشئ ملفاً (مثلاً `Ali.py`) واكتب فيه سطراً بسيطاً ثم احفظه بـ Ctrl + S.
- الأمر `git init` : يحول المجلد إلى مستودع Git (ينشئ مجلد `.git` المخفي، وهو يخزن بيانات المستودع وتاريخ الكائنات). ينفذ مرة واحدة فقط في المجلد الرئيسي.
- الأمر `git status` : يعرض الـ branch الحالي وحالة الملفات المتتبعة والمعدلة والمجهزة وغير المتتبعة. الأحمر يعني تغييراً لم يُجهّز، والأخضر يعني جاهزاً للحفظ.
- الأمر `git add اسم-الملف` : يجهّز ملفاً واحداً للحفظ، والأمر `git add .` يجهّز كل التغييرات (النقطة تعني كل ما في المجلد).
- الأمر `git commit -m "First"` : يحفظ لقطة (commit) برسالة First، ولكل commit رقم تعريف (hash).
- الأمر `git log` : يعرض سجل الـ commits. إذا علقت الشاشة فاضغط q للخروج.
- الأمر `git log --oneline` : يعرض كل commit بسطر واحد.
- تمرين Lab 1: أنشئ مشروع Python صغيراً، وسجّل إصدارين بـ commit مفهومين، ثم تحقق بـ `git log --oneline` أن فيه commits مختلفين.

### المرحلة 2: إنشاء مستودع فارغ على GitHub

- ادخل إلى موقع github.com بحسابك. (إذا لم يكن عندك حساب: افتح github.com ثم Register ثم أكمل التحقق المطلوب ثم افتح ملفك الشخصي.)
- اضغط علامة + أعلى يمين الصفحة ثم New repository.
- اكتب اسم المستودع في خانة Repository name.
- اختر الخصوصية: Public أو Private (شرحهما في فقرة المستودعات العامة والخاصة).
- اتركه فارغاً: لا تضف README ولا .gitignore ولا license، حتى يقبل أول رفع.
- اضغط Create repository.
- انسخ رابط HTTPS من الصفحة التي تظهر (أو من الزر الأخضر Code ثم HTTPS). شكل الرابط `https://github.com/<username>/<repository>.git`.
- في Lab 1: أنشأنا مستودعاً اسمه `testrepo` بخصوصية Private لهذا التمرين.

### المرحلة 3: ربط المشروع المحلي بـ GitHub وأول رفع

- الـ remote هو اتصال مسمى بمستودع Git آخر. والاسم `origin` اسم متعارف عليه وليس أمراً في Git، ويشير إلى رابط. ويمكن استخدام عدة remotes مثل origin و upstream.
- الأمر `git remote add origin <الرابط>` : يضيف المستودع البعيد ويسميه origin.
- الأمر `git remote` : يعرض أسماء الـ remotes.
- الأمر `git remote -v` : يعرض الأسماء مع الرابط مرتين، واحد للتنزيل (fetch) وواحد للرفع (push).
- الأمر `git branch` : يعرض الـ branch الحالي وتقف النجمة أمامه (عندنا master).
- الأمر `git push origin master` : يرفع الـ branch المسمى master إلى origin.
- الـ remote لا يعني أن GitHub يملك النسخة الوحيدة، فالمستودع المحلي نسخة كاملة أيضاً.
- عند أول رفع قد يفتح المتصفح ليطلب تسجيل الدخول إلى GitHub: ادخل بالحساب الصحيح ووافق (Authorize).
- علامة النجاح: ظهور السطر `* [new branch] master -> master`، وعند تحديث صفحة المستودع على GitHub يظهر الملف.
- ملاحظة: استخدم اسم الـ branch الفعلي عندك (master أو main). وتأكد منه بالأمر `git branch`.

### عن الـ git push بتفصيل أكثر (Lab 4-5)

- الأمر `git push` يرسل الـ commits إلى مستودع بعيد، ويشارك commits فرعك المحلي مع المتعاونين.
- يرفع الـ commits فقط. ولا يرفع التعديلات غير المحفوظة ولا المجهزة: لازم أولاً `git add .` ثم `git commit -m "..."` ثم `git push`.
- الصيغة: `git push <اسم-remote> <اسم-branch>`. مثال: `git push origin master` أو `git push origin feature-branch`.
- إذا كان الـ branch البعيد موجوداً يحدّثه، وإذا لم يكن موجوداً قد ينشئه إذا سمحت الصلاحيات. والمثال `git push origin feature-branch` يحدّث أو ينشئ `origin/feature-branch`.
- قائمة فحص قبل الرفع: أولاً احفظ بـ commit كل ما تريد نشره (بعد `git status`)، ثانياً تحقق من الـ remote بـ `git remote -v`، ثالثاً تحقق من الـ branch بـ `git branch`، رابعاً إذا تقدم الـ remote فاجلب التغييرات وادمجها أولاً.
- قد تؤثر على الرفع: المصادقة، وصلاحية الكتابة، وقواعد الـ branch.

### الـ Upstream والخيار `-u` (Lab 4-5)

- الـ upstream branch هو الـ branch البعيد الذي يتتبعه الـ branch المحلي. مثال: `master` المحلي يتتبع `origin/master`.
- فائدته: يستطيع Git أن يخبرك بحالة التقدم والتأخر (ahead/behind)، ويستخدم التتبع في pull و push.
- الأمر `git push -u origin master` : يرفع الـ branch ويربطه بالـ branch البعيد، فيتذكر Git أن لهذا الـ branch المحلي upstream على المستودع البعيد.
- الخيار `-u` اختصار لـ `--set-upstream`، فالأمران `git push -u origin master` و `git push --set-upstream origin master` متساويان.
- بعد ضبط الـ upstream يمكن غالباً كتابة `git push` فقط بدون وسائط. وهذا يرفع الـ branch الحالي ويستخدم الـ upstream المحفوظ.
- الأسماء يمكن أن تختلف: `git push -u origin master:feature` يعني الـ branch المحلي master يذهب إلى branch بعيد اسمه feature. الصيغة `git push -u <remote> <local-branch>:<remote-branch>`.
- تنبيه: وجود upstream لا يضمن نجاح `git push` المجرد. إذا اختلفت الأسماء (main يتتبع origin/feature) فإعداد push.default=simple قد يرفض `git push` المجرد. والحل الموثوق صيغة صريحة مثل `git push origin main:feature`.
- مثال من الملزمة: `git push -u githubrepo1 bug-fix` عند أول نشر، ثم تواصل العمل، ثم عدّل الكود و `git add .` و `git commit -m "Update the code"` ثم `git push` فقط.
- الفرق: `git push origin master` يرفع الـ branch المحدد بدون ضبط upstream صريح. أما `git push -u origin master` فيرفعه ويسجل `origin/master` كـ upstream له. ويستعمل `-u` عادة في أول رفع لـ branch محلي.

### المرحلة 4: تحديث الملف ورفعه (دورة العمل اليومية)

- عدّل الملف واحفظه بـ Ctrl + S.
- الأمر `git status` : يظهر الملف المعدل باللون الأحمر (modified).
- الأمر `git add .` : يجهّز التعديل.
- الأمر `git commit -m "Second"` : يحفظ commit جديداً.
- الأمر `git push origin master` : يرفعه إلى GitHub.
- علامة النجاح: سطر مثل `abc1234..def5678 master -> master`، وتسمى هذه العملية Fast-Forward لأن الـ commit الجديد جاء بعد آخر commit على GitHub مباشرة.
- بعد الرفع حدّث صفحة المستودع (F5) وتأكد أن عدد الـ commits زاد.

## ثالثاً: الـ commit الجيد

- لماذا رسالة الـ commit مهمة: تشرح غرض التغيير للفريق، وتسهل المراجعة (code review)، وتساعد المطور لاحقاً على تتبع عيب أو قرار، وتسهل العثور على التغيير المفيد في التاريخ.
- ممارسات جيدة: اجعل العنوان مختصراً ومحدداً (عادة حوالي 50 حرفاً).
- استخدم فعل أمر في أول العنوان: Add أو Fix أو Update أو Refactor.
- لا تضع نقطة في نهاية العنوان.
- يمكنك إضافة نص (body) اختياري يشرح ماذا تغيّر ولماذا.
- اجمع التغييرات المترابطة معاً، وافصل غير المترابطة.
- الـ commit الواحد الكبير يصعب صيانته: مثل "Add login, database, UI, reports, validation and colors"، فيه تعديلات غير مترابطة، ويصعب تتبع الخطأ أو التراجع عنه.
- الـ commits المركزة أسهل صيانة: Add login form ثم Add password validation ثم Fix login error.
- أنواع Conventional Commits الشائعة: `feat` وظيفة جديدة مثل `feat: add search filter`.
- النوع `fix` تصحيح خطأ مثل `fix: prevent empty password`.
- النوع `docs` تحديث توثيق مثل `docs: update README`.
- النوع `refactor` إعادة هيكلة الكود مثل `refactor: extract validator`.
- النوع `test` اختبارات آلية مثل `test: add login tests`.
- النوع `chore` مهام صيانة أخرى مثل `chore: update tooling`.
- الأمر `git commit --amend -m "Update task description"` : يستبدل آخر commit بنسخة معدلة. تحذير: تجنب تعديل commit تمت مشاركته مع الفريق إلا بتنسيق معهم.
- الأمر `git config --global core.editor "code --wait"` : يجعل VS Code هو المحرر الذي يستخدمه Git لرسائله عند الحاجة.
- الأمر `git config --global --get core.editor` : يعرض المحرر المضبوط حالياً. والمحرر الافتراضي يعتمد على إعداد Git، و Vim شائع على بعض الأنظمة.

## رابعاً: المصادقة والـ Personal Access Token (PAT)

- الاتصال بـ GitHub له طريقتان، والرابط يحدد أيهما يستخدم Git: HTTPS يعتمد على PAT عند طلب بيانات الدخول، و SSH يعتمد على زوج مفاتيح (مفتاح خاص ومفتاح عام).
- عنوان HTTPS يبدأ بـ `https://` ويعمل عبر اتصالات HTTPS، وقد يحتاج بيانات دخول أو token للكتابة.
- عنوان SSH يبدأ عادة بـ `git@github.com:` ويستخدم مفاتيح SSH، ويحتاج إعداداً قبل العمليات المصادَق عليها.
- تجد الخيارين في قائمة Code الخاصة بالمستودع.
- الـ token (رمز الوصول الشخصي) بديل عن كلمة سر حسابك عندما يتعامل Git مع GitHub عبر HTTPS. كان GitHub يقبل كلمة سر الحساب سابقاً لعمليات Git، وهذا النوع من المصادقة أُزيل.
- الآن عندما يطلب Git بيانات HTTPS تستخدم اسم حسابك مع PAT بدلاً من كلمة السر.
- الفائدة: يمكن تقييد الـ PAT وإلغاؤه دون تغيير كلمة سر حسابك.
- نوعان من الـ PAT: الـ classic (الذي تتبعه صور الملزمة) ويستخدم صلاحيات OAuth مثل `repo`. والـ fine-grained (يوصي به GitHub عموماً) ويمكنه تحديد المستودعات وصلاحيات أدق.
- الـ PAT يُستخدم في عمليات HTTPS: الرفع (Push) وتنزيل ودمج التغييرات (Pull).
- في الحالة العادية Git Credential Manager أو VS Code قد يسجل الدخول عبر المتصفح تلقائياً دون سؤال في الـ terminal.
- خطوات إنشاء classic PAT: اضغط صورة حسابك على GitHub ثم Settings.
- ثم Developer settings (في آخر القائمة اليسرى).
- ثم Personal access tokens ثم Tokens (classic).
- اضغط Generate new token ثم Generate new token (classic).
- اكتب اسماً في خانة Note يصف الغرض (مثل GitHub Test)، واختر مدة قصيرة في Expiration (مثل 30 days). وبعد الانتهاء تستخدم token جديداً.
- فعّل الصلاحية `repo` فقط، ولا تضف صلاحيات غير ضرورية. تأكد من الاسم والمدة والصلاحية قبل الضغط.
- اضغط Generate token وانسخ الـ token فوراً، لأن GitHub يعرضه مرة واحدة فقط.
- طريقة الاستعمال: عند `git push origin master` يطلب Git الاسم (Username) فتكتب اسم حسابك، ثم كلمة السر (Password) فتلصق الـ token مكانها (لا كلمة سر حسابك).
- لا تضع الـ token داخل رابط الـ remote أبداً.
- الأمان: عامل الـ token كأنه كلمة سر.
- استخدم الصلاحيات المطلوبة فقط ومدة انتهاء محدودة.
- لا تلصقه في كود أو مستودع أو صورة شاشة.
- إذا انكشف فألغه أو احذفه من إعدادات GitHub.
- قد ينتهي الـ token، فأنشئ جديداً عند الحاجة.
- طريقة بديلة عند تعليق نافذة تسجيل الدخول في VS Code: ننشئ token ونرفع بالأمر `GIT_ASKPASS= git -c credential.helper= push origin master` فيطلب الاسم وكلمة السر داخل الـ terminal. (جربناها كحل مقترح.)

## خامساً: مستودعات GitHub

### عام وخاص

- المستودع العام (Public): يراه أي شخص، ويناسب المشاريع المفتوحة، وتبقى صلاحيات المساهمة بحسب قواعد المستودع.
- المستودع الخاص (Private): متاح فقط للأشخاص المخولين، ويفيد المشاريع السرية للطلاب أو الشركات، ويستطيع المالك دعوة متعاونين.

### صفحة المستودع وتبويباتها

- بأعلى الصفحة: اسم المالك والمستودع، ومحدد الـ branch وقائمة الملفات، والـ README ووصف المشروع، وشريط التبويبات.
- تبويب Code: لتصفح الملفات والمجلدات وقراءة الكود من المتصفح بدون IDE، وللتنقل بين الـ branches، وللاطلاع على آخر الـ commits، وزر Code الأخضر يعطي عنوان المستودع وخيارات clone و ZIP.
- تبويب Issues: لمناقشة وتتبع الأخطاء وعناصر العمل.
- تبويب Pull requests: لاقتراح ومناقشة ودمج تغييرات الكود.
- تبويب Actions: لضبط أو فحص سير العمل الآلي.
- تبويب Projects: لتنظيم العمل بلوحة تخطيط.
- تبويب Security and quality وتبويب Insights وتبويب Wiki (إن كان مفعلاً): للأمان والإحصاءات والتوثيق الإضافي.
- تبويب Settings: إعدادات وصلاحيات، ويظهر بحسب صلاحياتك.
- ملف README.md: مقدمة المشروع، يشرح الغرض والخلفية، ويقدم تعليمات الإعداد والبناء والاستخدام، وقد يوثق قواعد المساهمة والاختبار، ويكتب عادة بصيغة Markdown ويظهر في الصفحة الرئيسية. اقرأه أولاً لتفهم المشروع قبل تفسير الكود أو اقتراح تغيير.
- الـ branch : خط تطوير منفصل داخل مستودع Git. والـ branch المختار يحدد الملفات والإصدارات التي تراها. مشروع Godot يستخدم master، وليست كل المشاريع تستخدم main.
- الـ Tag : علامة تشير إلى revision محدد، وتستخدم غالباً لتعريف إصدار.
- الـ Release : إصدار منشور مع ملاحظات إصدار، وأحياناً ملفات للتنزيل.

### أزرار متشابهة لكن مختلفة

- الـ Clone : ينشئ نسخة Git محلية مع التاريخ.
- الـ Download ZIP : ينزّل الملفات بدون تاريخ Git.
- الـ Fork : ينشئ نسختك الخاصة البعيدة من المستودع على حسابك.
- الـ Star : إشارة حفظ أو إعجاب بالمشروع.
- الـ Watch : اشتراك في إشعارات مختارة.

### إعدادات المستودع وتغيير الخصوصية (Lab 4-5)

- من صفحة المستودع افتح تبويب Settings.
- انزل إلى قسم Danger Zone واختر Change visibility واتبع خطوات التأكيد.
- تغيير الخصوصية (Change visibility): التبديل بين Private و Public، بحسب سياسة GitHub.
- أرشفة المستودع (Archive repository): يجعل المستودع للقراءة فقط مع حفظ محتواه.
- حذف المستودع (Delete repository): يزيل المستودع بعد تأكيد GitHub، وهو إجراء مدمّر.
- تحذير: تحويل مستودع خاص إلى عام قد يكشف الكود وكل التاريخ.
- المتعاونون: من Settings تجد Collaborators لمنح المتعاونين أو الفرق الصلاحية المناسبة، ومستوى الصلاحية يحدد ما يستطيع المساهم تغييره. وفي Danger Zone عمليات حساسة مثل الحذف أو نقل ملكية المستودع.

## سادساً: git clone و Download ZIP (Lab 6)

### الـ clone

- الـ clone ينسخ المستودع كاملاً من GitHub إلى جهازك: الملفات وكل التاريخ ومجلد `.git`، ويضيف origin تلقائياً.
- الـ clone يشبه تنزيل مجلد من الإنترنت، لكنه يعطيك كامل وظائف التحكم بالإصدارات.
- عندما تكون عضواً في مشروع يوجد خطوتان: الأولى الحصول على صلاحية الوصول للمستودع البعيد، فتقبل الدعوة (Accept invitation) من بريدك أو من إشعارات GitHub، والثانية تنفيذ `git clone`.
- رابط المستودع: صفحة المستودع ثم الزر الأخضر Code ثم HTTPS ثم Copy.
- أنشئ مجلداً جديداً ليس فيه `.git` (لا تنفذ clone داخل مجلد مشروع Git، حتى لا ينشأ مستودع داخل مستودع)، وافتح terminal داخله.
- الأمر `git clone <الرابط>` : ينشئ مجلداً باسم المستودع (إلا إذا حددت اسماً آخر) وينسخ فيه كل شيء.
- الأمر `cd <اسم-المستودع>` : يدخل المجلد الجديد.
- بعد الـ clone تجهّز بيئة التطوير، أو تنتقل إلى branch آخر لتبدأ عملك.
- الأمر `git remote -v` : يظهر origin بدون أن نضيفه نحن.
- الأمر `git log` : يظهر كل الـ commits، وعلى الأخير `HEAD -> master, origin/master, origin/HEAD`.
- الأمر `git branch` : يظهر master.
- الأمر `ls -a` : يظهر المجلد المخفي `.git` مع الملفات. وهذا أمر الـ shell وليس أمر Git.

### الـ Download ZIP

- من صفحة المستودع اضغط الزر الأخضر Code ثم Download ZIP، ثم فك الضغط.
- قد يظهر مجلد داخل مجلد بنفس الاسم بسبب الفك، فادخل المجلد الذي فيه الملفات.
- افتح terminal داخله ونفذ `git log` و `git remote -v` : يعطيان الخطأ `fatal: not a git repository` لأنه لا يوجد `.git`.
- الأمر `ls -a` : يظهر الملفات فقط بدون `.git`.
- الـ ZIP يحمّل لقطة (snapshot) من الملفات الحالية، ولا يشمل تاريخ الـ commits، ولا يحتوي مجلد `.git`، ولا اتصال له بالمستودع البعيد، والأمر `git log` يعطي خطأ.
- الـ clone ينشئ نسخة محلية من مستودع Git، ويشمل تاريخ الـ commits، ويحتوي مجلد `.git`، ويتصل تلقائياً بالمستودع البعيد (origin)، والأمر `git log` يعرض تاريخ الـ branch الحالي.
- الـ ZIP مناسب لرؤية الكود أو استخدامه فقط، والـ clone مناسب للتطوير والعمل الجماعي.

## سابعاً: الحالات الثلاث لبدء مشروع Git و GitHub

- الحالة 1: صاحب المشروع (Project Initiator). هو الذي يبدأ المشروع من الصفر.
- الخطوة الأولى لصاحب المشروع: الأمر `git init` ينشئ مستودعاً محلياً.
- الخطوة الثانية: يكتب الكود ويحفظه محلياً بالأوامر `git add` و `git commit` و `git status` و `git log`، ويمكنه استخدام ملف `.gitignore` لاستثناء ملفات لا يريد رفعها.
- الخطوة الثالثة: ينشئ مستودعاً بعيداً على GitHub من زر New repository، ثم يدعو المتعاونين من صفحة المستودع: Settings ثم Collaborators ثم Add people.
- الخطوة الرابعة: يربط المحلي بالبعيد بالأمر `git remote add origin <الرابط>` ويرفع بالأمر `git push origin master`.
- الحالة 2: عضو في المشروع (Project Member / Collaborator). يعمل على مستودع موجود أصلاً.
- الخطوة الأولى للعضو: يحصل على صلاحية الوصول، فيقبل الدعوة (Accept invitation).
- الخطوة الثانية: الأمر `git clone <الرابط>` ينشئ عنده مستودعاً محلياً.
- بعدها يساهم بتغييراته حسب الصلاحيات التي أُعطيت له.
- الحالة 3: شخص ليس عضواً في المشروع (Non-Project Member). يجد مستودعاً عاماً (Public) على GitHub.
- الخطوة الأولى: يضغط Fork فتنشأ نسخة تحت حسابه، ويصير هو مالك هذه النسخة ويطورها باستقلال.
- الخطوة الثانية: الأمر `git clone <رابط نسخته>` ينسخها إلى جهازه. انتبه أن الرابط هو رابط النسخة التي تحت حسابه، وليس رابط المستودع الأصلي.
- مثال الملزمة: المطور A هو صاحب المشروع الأصلي، والمطور B عضو فريق يدعم A، والمطور C مطور مستقل يريد الاستفادة من كود موجود ليطلق مشروعاً جديداً.

## ثامناً: الـ Fork (نسخة من مشروع شخص آخر)

- الـ Fork هو نسختك الشخصية على GitHub من مشروع شخص آخر. تجرب وتعدّل فيها بحرية دون أن يتأثر المشروع الأصلي.
- نحتاج Fork عندما نريد المساهمة بمشروع ولا نملك صلاحية الكتابة (write) على مستودعه الرئيسي.
- بعد أن ترضى عن تعديلاتك تنشئ Pull Request، وهو طلب لصاحب المشروع كأنك تقول: "عملت هذه التغييرات في نسختي، هل تريد إضافتها إلى المشروع الأصلي؟".
- يمكنك أيضاً استخدام النسخة للتعلم من الكود أو لتحسينه أو لتعديله حسب احتياجك.
- الخطوة 1: ابحث عن المستودع من خانة البحث أعلى GitHub (Type / to search)، واكتب اسمه بالشكل `owner/repository` ثم اختره.
- الخطوة 2: بصفحة المستودع اضغط زر Fork أعلى اليمين بجانب Star.
- الخطوة 3: تظهر صفحة Create a new fork. فيها خانة Owner وهي حسابك، وخانة Repository name وهي بنفس الاسم افتراضياً ويمكنك تغييره، وخانة Description اختيارية، ومربع Copy the master branch only.
- الخطوة 4: اضغط Create fork، فتصير النسخة تحت حسابك.
- الخطوة 5: من نسختك اضغط Code ثم HTTPS وانسخ الرابط. هذا رابط حسابك أنت.
- الخطوة 6: الأمر `git clone <رابط نسختك>` ينزّلها إلى جهازك، وتعمل عليها كأي مستودع ثاني.
- الفرق بين Fork و Clone: الـ Fork يتم على GitHub وينسخ المستودع إلى حسابك، والـ clone يتم على جهازك وينسخ مستودعاً بعيداً إلى حاسوبك. لذلك بالحالة 3 نستخدم الاثنين معاً، Fork ثم clone.
- مسار مساهمة نموذجي (مثال Godot): تعمل Fork للمستودع الأصلي (upstream)، ثم تنشئ branch، ثم تعمل commit و push، ثم تفتح PR. وبعد الـ PR: نقاش ثم فحوص آلية ثم مراجعة ثم دمج محتمل.
- بعد أن ترفع تعديلاتك إلى نسختك، ينشأ الـ Pull Request من صفحة نسختك على GitHub، من تبويب Pull requests ثم New pull request.

## تاسعاً: أدوات التعاون في GitHub (Issues و PR و Actions و Projects)

### الـ Issues

- الـ Issue بند عمل وليس دائماً خطأً برمجياً: قد يكون تقرير خطأ (bug report) أو طلب ميزة أو تغيير توثيق أو مهمة تقنية أو نقاشاً.
- يوثق الـ Issue: العنوان (وصف مختصر)، والوصف (ماذا حدث وكيف يتكرر)، والتصنيفات (Labels)، والمسؤولين (Assignees)، والتعليقات والحالة (Open أو Closed).
- يمكن تسجيل القرارات والتصنيفات والإحالات، وربط الـ Issue بـ branch أو Pull Request للتتبع.
- في Godot: متتبع `godotengine/godot` مخصص للأخطاء، والاقتراحات الجديدة تذهب إلى `godotengine/godot-proposals`.
- تقرير الخطأ المفيد: أولاً ابحث عن تقارير موجودة لتتجنب التكرار.
- ثانياً استخدم مشروعاً تجريبياً بأقل حالة تُظهر الخطأ (MRP).
- ثالثاً صف الخطوات والنتيجة الفعلية مقابل المتوقعة ليمكن تكرارها.
- رابعاً اذكر إصدارات Godot التي جربتها، وهل الخطأ تراجع (regression).
- معاني الـ Labels تختلف من مستودع لآخر، فاطلع على تصنيفات المستودع قبل تفسيرها.

### الـ Pull Request (PR)

- الـ PR اقتراح لدمج تغييرات من branch إلى آخر، كأنك تقول: "راجع فرعي وفكر في دمجه في الفرع الهدف".
- يعرض الملفات المتغيرة وتاريخ الـ commits، ويوفر تعليقات وموافقات مراجعة، ويساعد الفريق على فحص الجودة قبل الدمج.
- الـ PR ليس مثل commit مباشر على main، فهو يخلق فرصة منظمة للمراجعة.
- الـ commit المباشر: تدخل التغييرات الفرع مباشرة، ولا خطوة مراجعة مطلوبة، وقد يناسب المشرفين المصرح لهم.
- الـ PR: سجل واضح للتغيير المقترح، ونقاش ومراجعة زملاء، وفحوص آلية قبل الدمج.
- ما نفحصه داخل الـ PR: تبويب Conversation (الوصف والمبررات والنقاش وتعليقات المراجعة)، وتبويب Commits (المراجعات المقدمة)، وتبويب Files changed (الفروق: الأسطر المضافة أو المعدلة أو المحذوفة)، وتبويب Checks (البناء والاختبارات الآلية وحالتها)، وحالة المراجعة (موافقات أو طلبات تغيير).
- ماذا يفحص المراجع: الصحة (Correctness) هل يعالج السلوك المقصود، والقراءة (Readability) هل التغيير مفهوم وقابل للصيانة، والأسلوب (Style) هل يحترم أعراف المشروع، والاختبارات (Tests) هل هي موجودة وناجحة، والأمان والتصميم (Security & design) هل يتجنب المخاطر الواضحة.
- المسار من Issue إلى كود تمت مراجعته: Issue ثم Branch ثم Pull Request ثم Review ثم Merge.
- الفرق: الـ Issue يجيب "ما الذي يحتاج انتباهاً؟"، والـ PR يجيب "ما تغيير الكود المقترح؟". والـ Issue قد يشرح لماذا نحتاج PR، وكلاهما يحفظ نقاشاً قابلاً للتتبع.
- آداب المساهمة في Godot: اجعل الـ PR مركزاً (موضوع واحد لكل تغيير)، واقرأ إرشادات المشروع (ملف `CONTRIBUTING.md` وقواعد أسلوب الكود)، وقدم اختبارات حين تفيد، وناقش الأفكار الكبيرة عبر عملية الاقتراحات.

### الـ Actions و الـ Projects

- الـ GitHub Actions أتمتة تعمل عند أحداث المستودع: يحدث Push أو PR، ثم يعمل workflow، ثم بناء أو اختبار، ثم تقرير الحالة.
- أمثلة Godot: Linux Builds و Windows Builds و macOS Builds و Static Checks. وقد تتغير أسماء الـ workflows مع تحديث المشرفين.
- أهمية الفحص الآلي: يساهم مئات الأشخاص، فيجب التحقق تلقائياً.
- الـ Projects تتبع العمل عبر مستودعات، وتعرض لوحة وحالات. مثال لوحة Kanban: Backlog ثم Ready ثم In Progress ثم In Review ثم Done، وقد تعيد المراجعة العنصر إلى In Progress.
- الـ Labels تصنف العمل (bug و documentation و enhancement و good first issue)، والـ Assignees تجعل المسؤولية واضحة، والـ Filters تبحث بالتصنيف أو الحالة أو المؤلف أو المسؤول أو عبارة بحث.
- أهم ثلاثة أشياء في الاستخدام اليومي: Code (قراءة المستودع ومتابعة الإصدارات) و Pull Requests (مراجعة التغييرات قبل الدمج) و Projects (رؤية المسؤوليات والتقدم).
- لماذا المشاريع المفتوحة المصدر مفيدة: كودها متاح علناً بترخيص مفتوح، فيمكن دراسة تنظيم مشروع حقيقي وأساليب برمجته، وتُظهر الـ Issues والـ PR كيف يناقش الفريق أعمال الصيانة، وتلتزم المساهمة بقواعد كل مشروع.

## عاشراً: ملف .gitignore وملف Markdown (Lab 4-5)

- ملف `.gitignore` يسرد الملفات والمجلدات غير المتتبعة التي يجب أن يتجاهلها Git.
- فائدته: تجنب رفع الملفات المؤقتة وملفات البناء وبيانات البيئة المحلية.
- الأداة المذكورة بالملزمة: gitignore.io، تعطي أنماط تجاهل نموذجية لتقنيات المشاريع.
- الخطوات: اختر نوع المشروع مثل Django أو Python، ثم اضغط Create لترى الأنماط المقترحة، ثم انسخ النص الناتج والصقه في ملف `.gitignore` في جذر المستودع.
- تنبيه: Git لا يتوقف عن تتبع ملف متتبع أصلاً لمجرد أنه صار مكتوباً في `.gitignore`.
- ملف README يُكتب بـ Markdown. الصيغة: علامة `#` للعناوين، و `**نص**` للخط العريض، وعلامة `-` للقوائم النقطية.
- الأداة المذكورة: Markdown Live Preview، تعرض صيغة المصدر بجانب النتيجة المنسقة.

- الخطوة 6: انتظر النشر، فيبدأ GitHub تلقائياً. علامة الصح الخضراء في حالة العملية تعني النجاح.

## ثاني عشر: أخطاء واجهتنا وحلولها

- الخطأ `unknown subcommand` عند كتابة `git remote -v <الرابط>` : الخيار -v يعني "اعرض" فقط. الصحيح `git remote add origin <الرابط>`.
- الخطأ `403 Permission denied to <حساب آخر>` عند الرفع : الجهاز مسجل بحساب غير حساب المستودع. الحل: افتح Credential Manager من قائمة ويندوز ثم Windows Credentials، ودوّر تحت Generic Credentials على `git:https://github.com` وافتحه واضغط Remove (لا تحذف غيره). ثم أعد `git push origin master` وسجّل الدخول بالحساب الصحيح.
- الخطأ `src refspec origin does not match any` عند كتابة `git push add origin master` : كلمة add زائدة، لأنها لـ `git remote add` فقط. الصحيح `git push origin master`.
- الخطأ `The most similar command is status` عند كتابة `git ststus` : خطأ إملائي، وGit يقترح الأمر الصحيح.
- الخطأ `has no upstream branch` عند كتابة `git push` فقط أول مرة : لا يوجد ربط. الحل `git push origin master` أو `git push -u origin master`.
- الشاشة التي علقت بعد `git log` : هذا الـ pager، فاضغط q.
- الخطأ `'ls' is not a git command` عند كتابة `git ls -a` : أمر ls ليس من Git. الصحيح `ls -a`.
- الخطأ `fatal: not a git repository` : المجلد لا فيه `.git` (مثل مجلد الـ ZIP). الحل `git clone` أو `git init`.
- الخطأ `rejected` عند الرفع : المستودع البعيد فيه commits أحدث. الحل `git pull` ثم `git push`.
- الخطأ `Authentication failed` : التوثيق ناقص أو خاطئ. الحل استخدام token صحيح.
- الرفع لا يرفع تعديلاتك : لأن `git push` يرفع الـ commits فقط، فتأكد أنك عملت `git add .` ثم `git commit` قبله.

## ثالث عشر: مفاهيم سريعة

- الـ commit : لقطة محفوظة للمشروع لها رقم (hash).
- الـ branch : اسم يقف على commit، ولا يتحرك إلا عندما تعمل commit وأنت واقف عليه.
- الـ master : مجرد الاسم الافتراضي للـ branch الأول، وتأكد من اسمه بالأمر `git branch`.
- الـ HEAD : يشير إلى الـ branch الذي أنت عليه.
- الـ detached HEAD : يحدث عندما تنتقل إلى commit قديم بالأمر `git checkout <hash>`، ويرجع الوضع الطبيعي بالأمر `git checkout master`.
- الـ origin : لقب محلي للرابط البعيد.
- الأمر `git pull` : يجمع خطوتين، fetch أي التنزيل ثم merge أي الدمج. نستخدمه قبل push إذا رفض Git الرفع، وقد يظهر تعارض (conflict) إذا عدّلتما نفس السطر.
- الـ upstream : الـ branch البعيد الذي يتتبعه الـ branch المحلي.

## رابع عشر: ما لم ننفذه عملياً بعد

- الـ SSH.
